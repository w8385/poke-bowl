# poke-bowl 데이터 기준점

## 우선순위

### 1. PokeAPI
사용 목적:
- 구조화 기초 데이터의 기본축
- 도감번호, 영문명, 타입, 종/폼 식별자 확보
- 앱 내부 slug/기본 엔터티 생성의 출발점

### 2. Serebii
사용 목적:
- 볼/입수 가능 여부, 세대별 예외, 실제 게임 내 가능 조합 검증
- 구조화 데이터에 없는 실사용 맥락 보강

### 3. Pokémon Database
사용 목적:
- 사람이 읽는 기본 사실 교차확인
- 이름/타입/도감 정보 빠른 보조 검증

### 4. Bulbapedia
사용 목적:
- 예외 케이스 확인
- 이벤트/이전작/특수 경로 보조 참고
- 주 기준이 아니라 보조 확인용

## poke-bowl에서 지금 필요한 최소 데이터 기준

MVP에서 먼저 고정할 데이터는 아래뿐이다.

### A. 포켓몬 기본 식별 정보
- 전국도감 번호
- 영문 canonical slug
- 한글명
- 영문명
- 타입
- 필요 시 폼명

기준:
- 기본 구조화 데이터는 **PokeAPI**를 기준으로 잡는다
- 이름/번호/타입은 **Pokémon Database + Serebii**로 교차확인한다
- slug는 서비스 내부 규칙으로 고정

### B. 볼 기본 메타 정보
- 볼 key
- 한글명
- 영문명
- 희소성/특수성 정도의 간단 분류

기준:
- 볼 이름/종류 자체는 **Serebii + Pokémon Database** 기준
- 색감/디자인 태그는 내부 큐레이션

### C. 입수 가능 여부 / 합법성 상태
- `official`: 현재 기준 큰 이슈 없이 사용 가능하다고 확인된 조합
- `limited`: 이벤트/이전작/한정 루트 의존성이 커서 주의 필요한 조합
- `check`: 아직 교차확인 덜 끝난 조합

기준:
- **Serebii를 1차 기준**으로 둔다
- Pokémon Database는 보조 확인
- Bulbapedia는 예외 조사시에만 사용
- PokeAPI는 이 레이어의 주 근거가 아니라 기본 포켓몬 엔터티 참조용이다

### D. 추천 그 자체
- 추천 볼 1개
- 대체 볼 1~2개
- 짧은 추천 이유

기준:
- 이 부분은 사실 데이터가 아니라 **운영자/커뮤니티 큐레이션**
- 즉 투표는 '사실 검증'이 아니라 **추천 선호도 수집**으로 본다

## 로그인/투표 설계 전에 고정할 원칙

1. **사실 데이터와 취향 데이터를 분리한다**
   - 사실: 이름, 타입, 볼 존재, 입수 가능 여부
   - 취향: 어떤 볼이 가장 잘 어울리는지

2. **투표 대상은 운영자가 먼저 올린 후보군 안에서만 받는다**
   - MVP에서는 임의 볼 자유입력 금지
   - 각 포켓몬마다 `대표 추천 1 + 대체 1~2` 정도 후보만 투표

3. **합법성 상태가 `check`인 항목도 노출은 가능하지만, 경고를 붙인다**
   - 투표 가능 여부와 합법성 확정 여부는 별개로 본다

4. **Bulbapedia 단독 근거로 status를 올리지 않는다**
   - 보조 참고만 허용

## 지금 바로 쓰는 운영 규칙

- 포켓몬 기본 구조화 데이터: PokeAPI
- 포켓몬 기본 정보 교차확인: Pokémon Database + Serebii
- 볼/입수 가능 여부: Serebii 우선
- 위키성 보강: Bulbapedia 보조
- 추천 볼/이유: 내부 큐레이션
- 유저 투표: 내부 큐레이션 후보군에 대한 선호도 수집
